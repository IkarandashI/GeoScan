## 1. Резюме предлагаемого подхода

| Область | Предлагаемое решение | Почему |
|---|---|---|
| Физическая модель | **Patched conics** (сферы влияния) + **аналитические кеплеровы орбиты** + **Lambert-перелёты** + мгновенные импульсы ΔV | ТЗ прямо разрешает упрощения («не требуется N-body, полноценная орбитальная механика»). Аналитика даёт детерминизм, мгновенную пропагацию на годы вперёд (time warp бесплатно) и быстрые прогоны для планировщика. Gravity assist в этой модели возникает естественно |
| Планировщик | **Beam search по графу тел** (последовательности перелётов), стоимость ребра из **реестра критериев** (Fuel / Time / Risk + любые новые) | Разделяет «алгоритм поиска» и «критерии оптимальности» — прямое выполнение требования про расширяемость без правки кода |
| Риск | Нормированная модель на базе перицентра пролёта, v∞, запаса топлива на коррекции; жёсткие нарушения → манёвр **недопустим** | Соответствует разделу «Риск» ТЗ один в один |
| Конфигурация | `UDataAsset`-сценарий (редактируется в редакторе UE = «конфигуратор») + экспорт/импорт JSON | Данные полностью отделены от логики, плюс закрывает доп-требование save/load |

Разделение домена и движка — на уровне папок и правил включений |

## 2. Физическая модель

### 2.1 Система отсчёта и единицы
- Физика — в **double, единицы СИ** (метры, секунды, кг). Начало — центр звезды, инерциальная система. `FVector` в UE5 по умолчанию double (Large World Coordinates) — домен использует UE-типы без потери точности.
- Гравитационный параметр `μ = G·M` хранится сразу для каждого тела (не пересчитываем из G и массы каждый раз). G = 6.674e-11.
- Рендер-слой переводит метры в юниты UE отдельно (см. [8.1](#81-масштаб)) — float-точности UE хватает только из-за сжатия.

### 2.2 Patched conics и сферы влияния (SOI)
- Каждое тело имеет **сферу влияния**: внутри SOI тела гравитирует **только оно**; вне всех планетных SOI — только звезда. Никакой суперпозиции (это и есть «упрощённая» модель вместо N-body).
- SOI планеты вычисляемая: `r_SOI = a_orb · (m_p / M_star)^(2/5)`; в данных тела предусмотрен оверрайд фиксированным значением (ТЗ: «может быть фиксированной или вычисляемой»).
- SOI звезды = вся система до границы (Target Distance).
- Иерархия: тело знает `ParentBody`. Планеты — дети звезды. Модель сразу допускает луны (дети планет) — расширяемость без переделки физики, но по умолчанию генератор луны **не создаёт** (за рамками ТЗ).

### 2.3 Движение небесных тел
- **Круговые орбиты**: `θ(t) = θ0 + ω·t`, `ω = sqrt(μ_parent / r³)`. Позиция — чистая функция времени ⇒ полностью детерминировано, эфемериды тела в любой момент t планируемости.
- `Orbital Velocity` — вычисляемая: `v = sqrt(μ_parent / r)` (пункт ТЗ «вычисляемые параметры»).
- Наклонение (`Orbital Inclination`) — опция генератора: поворот плоскости орбиты. **По умолчанию предлагаю компланарную систему** (наклонения = 0, флаг включает) — вопрос [Q3](#11-открытые-вопросы).

### 2.4 Движение аппарата
- Между манёврами аппарат на **кеплеровой конике** относительно доминирующего тела (эллипс/гипербола/парабола). Пропагация — аналитическая, через решение уравнения Кеплера (универсальная формулировка переменных, чтобы одна ветка кода покрывала все типы коник).
- При пересечении границы SOI — смена доминирующего тела: скорость просто переразлагается (скорость относительно нового тела = v_sc − v_body; patched conics стандартно так работает, удар импульса не нужен).
- Стартовое состояние: круговая орбита радиуса `StartingOrbitRadius` вокруг Starting Body, `Initial Spacecraft Velocity = sqrt(μ_body / r_start)` (вычисляемая, как в ТЗ).

### 2.5 Манёвры и топливо
- Манёвр = **мгновенный импульс ΔV** в точке траектории. Расход топлива — ракетное уравнение Циолковского:
  `Δm_fuel = m0 · (1 − exp(−ΔV / (Isp · g0)))`.
- Бюджет: `ΔV_max = Isp · g0 · ln(m0 / m_dry)` — жёсткое ограничение; ребро маршрута с превышением — недопустимо, а не «дороже».
- `Current Spacecraft Mass = DryMass + FuelRemaining` — вычисляемая, уменьшается по мере расхода (ТЗ).
- `MaxThrust` используется в **исполнении плана** (см. [7.2](#72-исполнение-плана)): опция «конечная тяга» — импульс разыгрывается серией включений двигателя длительностью `t_burn = m·ΔV/F`. По умолчанию — мгновенные импульсы (план и исполнение совпадают 1:1); конечная тяга включается флагом и служит источником ошибок исполнения для демо replanning.

### 2.6 Гравитационные манёвры (gravity assist)
- Вход в SOI планеты с гиперболической скоростью v∞. Перицентр `r_p ≥ R_body` (+ запас безопасности).
- Максимальный угол поворота вектора v∞: `δ_max = 2·asin(1 / (1 + r_p·v∞²/μ))` — чем меньше v∞ и ближе (безопаснее) перицентр, тем больше поворот.
- Планировщик использует пролёт как ребро «пришёл с v∞_in, вышел с v∞_out, |угол между| ≤ δ_max» — бесплатное изменение гелиоцентрической скорости. Если требуемый поворот чуть больше δ_max — либо ребро недопустимо, либо платим малый ΔV на подгонку (решение в реализации, честно задокументируем).
- Топливо на assist не тратится (кроме опциональной коррекции) — в этом смысл манёвра.

### 2.7 Перелёты между телами (Lambert)
- Ребро «тело A → тело B за время T» решается **Lambert solver'ом** (универсальные переменные, алгоритм по Vallado; ограничение до 0–1 витков). Даёт вектор скорости отлёта/прилёта на гелиоцентрической баллистике.
- Стоимость стыковки: `ΔV_depart = |v_depart_Lambert − v_A|`, `ΔV_arrive = |v_arrive_Lambert − v_B|` (прилёт с ненулевой v∞ — это как раз «топливо» следующего assist'а, если B — пролётное тело).
- Фазирование: перебор окна старта (время ожидания на орбите) × времени перелёта — мини-«porkchop» сеткой, берём лучшие N вариантов. Грубая сетка → локальное уточнение.
- Edge cases (трансфер 0°/180°, сходимость итераций) закрываются юнит-тестами (см. [12, M1](#12-план-работ)).

### 2.8 Что сознательно НЕ делаем
Из раздела «Не требуется»: N-body, реалистичные системы, полноценная орбитальная механика (наклонения аппарата, возмущения, не-кеплеровы траектории), красивый UI/рендер. Это фиксируем в README, чтобы проверяющий видел осознанный scope.

## 3. Планировщик маршрута

### 3.1 Постановка
Вход: эфемериды системы (функции времени), состояние аппарата (массы, Isp, стартовая орбита), набор критериев с весами, ограничения (MaxFlightTime, топливо, радиусы тел).
Выход: **план миссии** — упорядоченный список событий: ожидание → манёвры (время, ΔV-вектор, назначение) → пролёты/assist'ы → финальный разгон; + интегральные метрики (TotalΔV, FlightTime, Risk) и полная траектория для предпросмотра.

### 3.2 Интерфейс и реализации
- `IRoutePlanner` (чистый C++): `Plan(context) → FRoutePlan`. Планировщик **не знает** конкретных критериев и откуда взялся конфиг — требование ТЗ «конфигурация не жёстко связана с алгоритмом».
- Реализации:
  - `FBeamSearchPlanner` — основная (ниже);
  - `FBruteForcePlanner` — полный перебор последовательностей до малой глубины, для тестов и бенчмарка сравнения;
  - выбор реализации — поле в конфиге сценария.
- Параметры поиска (beam width, max hops, сетка porkchop, окно фазирования) — тоже конфиг, не код.

### 3.3 Beam search по последовательностям тел
1. **Уход со стартовой орбиты**: ΔV с круговой орбиты на гиперболу отлёта (направление v∞ выбирает решатель).
2. Узел поиска = (текущее тело, состояние на входе: v∞, время). Расширение: для каждого следующего тела-кандидата — porkchop-сетка лучшего окна, стыковка с предыдущим состоянием (в т.ч. через assist-пролёт), частичная стоимость.
3. Пролёт тела может быть: (а) транзитным с гравманёвром (без захвата), (б) с захватом на орбиту (не делаем по умолчанию — см. [Q6](#11-открытые-вопросы)). Повторные пролёты одного тела разрешены (это и есть цепочки assist'ов), с лимитом hops.
4. **Финал**: от последнего тела (или гелиоцентрично) — манёвр на траекторию с апоапсисом ≥ границы системы; момент «расстояние до звезды ≥ Target Distance» = успех.
5. Отсечение ветвей: топливо исчерпано, время > MaxFlightTime, перицентр < радиуса тела, |v| > MaxSpeed (если задана), поворот assist'а > δ_max.
6. Beam width: на каждом уровне оставляем лучшие B частичных планов по текущей взвешенной стоимости. Финальный — лучший из достигших границы.

### 3.4 Критерии стоимости (расширяемость)
- `IRouteCostCriterion` (чистый C++): `Evaluate(FRouteMetrics) → double [0..1]` + `FName Id`.
- Из коробки: `FuelCriterion` (TotalΔV / ΔV_бюджет), `TimeCriterion` (FlightTime / MaxFlightTime), `RiskCriterion` (см. 3.5).
- **Критерии — `URouteCriterion : UObject` (Blueprintable)**: конфиг сценария хранит массив экземпляров `{ Criterion, Weight }`; планировщик вызывает `Criterion->Evaluate(Metrics)` и суммирует `Σ wᵢ·cᵢ`. Новый критерий = новый класс C++ или **даже Blueprint-ассет** (через BlueprintNativeEvent); веса/набор меняются конфигом — код планировщика не трогаем. Это прямое выполнение требования про многокритериальность и расширяемость.
- Режимы ТЗ — просто пресеты весов в конфигураторе:
  - Fuel Efficient: `Fuel=1.0, Time=0.0, Risk=0.0`
  - Time Efficient: `Fuel=0.0, Time=1.0, Risk=0.0`
  - Balanced: `Fuel=0.6, Time=0.3, Risk=0.1` (значения редактируемые)
  Нормализация каждого критерия в [0;1] обязательна, чтобы взвешенная сумма была осмысленна.

### 3.5 Модель риска
Для каждого сближения/пролёта:
- `d_factor`: близость перицентра к поверхности — 0 при `r_p ≥ R_body + Margin`, растёт до 1 при `r_p → R_body`;
- `v_factor`: `v∞ / v_max_rel` — чувствительность к ошибкам растёт со скоростью сближения;
- `c_factor`: дефицит бюджета коррекции — чем меньше остаток ΔV для исправления ошибок наведения, тем выше риск.
- `RiskFlyby = clamp(wd·d_factor² + wv·v_factor² + wc·c_factor, 0, 1)`; веса факторов — параметры модели в конфиге.
- `RiskCost` маршрута = max по манёврам (худший пролёт определяет риск всей цепочки) — с опцией «среднее» в конфиге.
- **Жёсткие нарушения** (перицентр < радиуса тела, превышение макс. скорости, топлива не хватает на минимальный корректирующий запас) — манёвр недопустим, ребро отбрасывается. Рост стоимости — только для «почти нарушенных» условий. Ровно как требует ТЗ.

## 4. Конфигурация сценария

### 4.1 Носитель
- `UScenarioConfig : UPrimaryDataAsset` — редактируется через Content Browser (Create Data Asset) = «конфигуратор сценария» из ТЗ. Один ассет = один сценарий; в контенте лежит 3+ готовых пресета (по одному на режим оптимизации).
- Подсекции (структуры):
  - `FSystemGenConfig`: Seed, NumPlanets, MinOrbitalRadius, (MaxOrbitalRadius, плотность распределения радиусов/масс/типов — параметры генератора), BoundaryMode: `Fixed(TargetDistance)` | `Relative(K × R_outermost)`, bInclinations, таблица типов тел.
  - `FSpacecraftConfig`: DryMass, FuelMass, MaxThrust, Isp, StartingBodyId, StartingOrbitRadius, InitialOrbitalPosition, MaxFlightTime, MaxSpeed, MarginSafety.
  - `FOptimizationConfig`: PlannerType, Criteria: TArray<{Id, Weight}>, параметры поиска (BeamWidth, MaxHops, porkchop grid).
  - `FVisualsConfig`: маппинг `TypeId → BP-класс тела`, масштаб отображения.
- Валидация при старте (лог-ошибки + отказ запуска сценария): Starting Body существует и не самое внешнее тело (требование ТЗ), FuelMass > 0, орбита старта > радиуса тела, и т.п.

### 4.2 Соответствие ТЗ
- «Параметры аппарата и миссии — из конфигурации, не хардкод» ✔ — симуляция и планировщик принимают только структуры конфига.
- «Параметры фиксированы всю миссию, кроме топлива/массы» ✔ — мутабельны ровно два поля состояния.
- «Начальное положение — в конфигураторе» ✔.
- Save/load (доп. требование): сериализация конфига и сгенерированной системы в JSON (GeneratedScenario.json в Saved/) + загрузка по кнопке в меню. JSON — ручной (JsonUtilities), чтобы формат был стабильным и diff-аемым в git.

### 4.3 Детерминизм
- Генератор системы работает от собственного RNG (**PCG32**, фиксированная реализация в ядре, seed из конфига) — один seed ⇒ побитово одна и та же система на любой платформе и любом запуске (доп. требование «deterministic random seed»). `FRandomStream` не используем — привязка к движку и платформе.

## 5. Архитектура: модули, C++/Blueprint

### 5.1 Модуль и раскладка (решение Q2: один модуль)

```
Source/GeoScan/            # единственный runtime-модуль
  GeoScan.Build.cs
  Core/                    # домен: обычные C++ типы (UE-типы разрешены, UObject — нет)
    PCGRng.h/.cpp            # детерминированный RNG (PCG32, от seed)
    OrbitMath.h/.cpp         # коники, Kepler solver (universal variables), SOI, Циолковский
    Lambert.h/.cpp           # Lambert solver
  Gen/                     # процедурная генерация системы по seed (детерминированно)
  Planner/                 # URouteCriterion, модель риска, beam search, план миссии
  Sim/                     # FSimState, события миссии, успех/провал, replan
  Config/                  # UScenarioConfig (DataAsset), JSON импорт/экспорт
  Actors/                  # ACelestialBody, ASpacecraft
  Systems/                 # USimWorldSubsystem (тик, time warp), спавн системы
  Render/                  # отрисовка орбит/траекторий, debug-визуализация
  UI/                      # C++-база виджетов, UMG-слой в BP
  Tests/                   # automation-тесты (под WITH_DEV_AUTOMATION_TESTS)
```

Правило слоёв: `Core/Gen/Planner/Sim` не включают заголовки UObject-слоя (`Actors`, `Config`, `UI` и т.д.); зависимости направлены только из UE-слоя в домен. Папка — не граница компиляции (модуль один), но граница ревью: нарушение правила — замечание на ревью. Automation-тестами покрывается весь домен прямо в движковом окружении.

### 5.2 Ядро (типичный список)
- `FCelestialBodyState` (Id, TypeId, ParentId, μ, Radius, орбитальные элементы, SOI), позиция/скорость как функции времени;
- `FSpacecraftState` (позиция, скорость, масса, топливо, текущая SOI);
- `FManeuver { Time, DeltaV, Note }`, `FRoutePlan { Maneuvers[], Metrics, Trajectory[] }`;
- `ISystemEphemeris` — доступ к телам/позициям по времени (то, что планировщик и симуляция получают извне).

### 5.3 UE-слой
- `USimWorldSubsystem : UWorldSubsystem` — владеет запущенной миссией: применяет конфиг, генерирует систему, спавнит акторы, тикает симуляцию, реализует **time acceleration** (множители, напр. 1×/10×/60×/3600×/1e5×), рассылает события (`OnManeuverExecuted`, `OnMissionResult`) в BP.
- `ACelestialBody` — данные (из ядра) + визуальный компонент (StaticMesh сфера + материал; масштаб по [8.1](#81-масштаб)). BP-подклассы для типов: `BP_Star`, `BP_Planet_Rocky`, `BP_Planet_GasGiant` — **новые типы тел = новый BP + запись в таблице конфига**, код не меняется (требование ТЗ).
- `ASpacecraft` — текущее состояние (из ядра), маркер/стрелка, трейл.
- Отрисовка линий — `ULineBatchComponent`/persistent debug lines (простота; красота не требуется) — орбиты тел, план миссии, фактическая траектория, SOI, v∞-векторы.
- Камера: свободный орбитальный Pawn + «фокус на теле» по клику/клавише; масштаб от системы к аппарату.

### 5.4 Разделение C++ / BP (требование ТЗ)
| C++ | Blueprint |
|---|---|
| Вся математика, физика, генерация, планировщик, симуляция, критерии | Визуальные подклассы тел (материалы, декомпозиция) |
| Конфиг-структуры (UDataAsset C++ база) | Конфиг-ассеты сценариев (создание/настройка в редакторе) |
| База виджетов (свойства, события) | UMG-макет HUD, экранов меню/итога |
| Subsystem, акторы, компоненты отрисовки | Связки ввода, простые анимации, вызовы консольных команд |

Критерий: в BP нет формул и циклов поиска; в C++ нет визуала/материалов.

## 6. Симуляция полёта

### 6.1 Игровой цикл и время
- Симуляция — событийно-аналитическая: `SimTime` двигается на `Δt·TimeWarp` каждый кадр; положение тел и аппарата — аналитические функции SimTime (поэтому ускорение времени не бьёт точность — доп-требование «time acceleration» почти бесплатно).
- Очередь событий: манёвры (время), пересечения SOI, проверка условий конца. Между событиями интеграция не нужна вовсе.

### 6.2 Исполнение плана
- План (из планировщика) = список манёвров с абсолютным временем. При `SimTime ≥ t_maneuver` применяется импульс (или конечная тяга, см. [2.5](#25-манёвры-и-топливо)) с опциональной ошибкой исполнения (`ExecutionErrorSigma` в конфиге — источник для демо replanning).
- Fail-safe: если топлива на манёвр не хватает — манёвр пропускается, миссия помечается failing (ограничение ТЗ «не может израсходовать больше топлива»).

### 6.3 Условия успеха/провала
- **Успех**: расстояние до звезды ≥ Target Distance (граница).
- **Провал**: столкновение/пересечение поверхности тела (r < R_body), топливо исчерпано при недостигнутой цели, FlightTime > MaxFlightTime (если задано), |v| > MaxSpeed (если задано).
- Результат + метрики (ΔV потрачено, время, остаток топлива, число манёвров, риск) — на экран итога и в лог.

### 6.4 Replanning (доп. требование)
- Кнопка «Replan» (и/или авто-триггер при ошибке исполнения > порога): планировщик перезапускается от текущего состояния (текущая позиция/скорость/масса), новый план подменяет хвост старого. Благодаря разделению IRoutePlanner это тот же вызов с другим стартовым контекстом.

## 7. Визуализация и UI

### 7.1 Масштаб
- Физика в метрах; рендер: `1 AU = RenderScale uu` (конфиг), радиус тела на экране = `max(trueRadius·RenderScale, MinVisualRadius)` — тела всегда видимы, орбиты различимы. Честный одномасштабный вариант технически возможен (флаг), но по умолчанию выключен.

### 7.2 Что рисуем
- Орбиты всех тел (окружности/эллипсы), SOI (полупрозрачные сферы, toggle), план миссии (пунктир), фактический трейл аппарата, маркеры манёвров, v∞-векторы на assist'ах (debug toggle), подписи тел.
- Debug-visualization (доп. требование): переключатели (`showdbg Orbits`, `SOI`, `Plan`, `Candidates` — отклонённые ветки beam search и их стоимости).

### 7.3 UI (UMG, минимальный)
- HUD: время миссии + warp, масса/топливо/ΔV-бюджет, текущая SOI, скорость, расстояние до звезды, следующий манёвр (обратный отсчёт, ΔV), прогресс до границы.
- Стартовая панель: выбор сценария-ассета, режим оптимизации/веса, seed, кнопки Generate / Plan / Launch.
- Экран итога: успех/провал + причина + метрики.
- Управление: пауза, time warp +/-, replan, фокусы тел.

## 11. Журнал решений (было: открытые вопросы)

> Решения зафиксированы 2026-09-26 по итогам обсуждения. Пересмотреть можно — правим этот раздел.

- **Q1. Физическая модель** → ✅ **Аналитические конусы + Lambert solver** (patched conics). Обоснование и детали — [раздел 2](#2-физическая-модель).
- **Q2. Организация кода** → ✅ **Один модуль `GeoScan`**. Домен (математика/генерация/планировщик) — обычные C++ типы в папках `Core/Gen/Planner/Sim`; UObject/USTRUCT — только там, где нужны редактор/BP/сериализация (конфиги, критерии, акторы, subsystem). Замечание к обсуждению снято: в UE5 `FVector` = double (Large World Coordinates), «float-проблемы» нет.
- **Q3. Орбитальные плоскости** → ✅ **Компланарная система по умолчанию**; наклонения модель поддерживает (поворот плоскости орбиты), включаются флагом генератора `bInclinations`.
- **Q4. Визуальный масштаб** → ✅ **Сжатие расстояний + минимальный видимый радиус тел**. Уточнение по ходу обсуждения: в ТЗ масштаб отображения действительно никак не зафиксирован (там лишь «красивый UI и реалистичный рендер не требуются») — это чисто инженерное решение. При честном масштабе и астрономических дистанциях планеты — невидимые точки, демонстрация планировщика невозможна. Поэтому: физика в честных метрах (double), рендер через конфигурируемый множитель (`1 AU = N uu`) и `MinVisualRadius`; переключатель «честный масштаб» остаётся как demo-опция. Решение чисто рендеровое и полностью обратимо конфигом.
- **Q5. Захват на орбиту промежуточных тел** → ✅ не делаем (только пролёты/assist'ы) — захват всегда дороже по топливу, в ТЗ его нет.
- **Q6. Лунные системы** → ✅ модель данных поддерживает (`ParentBody`), генератор по умолчанию не создаёт.
- **Q7. Внешние форматы сценариев** → ✅ не делаем, только наш JSON.
- **Q8. Имя проекта** → ✅ оставляем `GeoScan` (переименование — риск и время, не оценивается).
- **Q9. Версия движка** → ✅ UE 5.8 (как в `.uproject`), движок: `D:\UE_5.8`.

### Осознанно вне скоупа (по разделу «Не требуется» ТЗ)
N-body, возмущения, не-кеплеровы траектории, реалистичные системы, красивый UI/рендер. Фиксируется в README.

## 13. Замеченные тонкости ТЗ (чтобы не потерять)
- «Orbital Velocity — вычисляемая» ⇒ не поле, а функция тел.
- «Параметры аппарата фиксированы, кроме топлива и массы» ⇒ мутабельны ровно 2 величины.
- «Starting Body не самое внешнее тело» ⇒ валидация конфига.
- «Столкновение/превышение — манёвр недопустим, а не дороже» ⇒ в коде это отсечение ребра, не штраф в стоимости.
- «Критерии и приоритеты — из конфигурации, без изменения кода планировщика» ⇒ реестр критериев, а не switch по enum.
- «Max Thrust» присутствует, но при мгновенных импульсах не нужен ⇒ используем в опции конечной тяги (2.5), чтобы параметр не висел мёртвым.
